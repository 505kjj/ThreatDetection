# Phase 8A academic deployment

Use Vercel Hobby for the generated public site, one Render Free Docker web service for the Java 21 API and administrator console, and one Neon Free PostgreSQL project for monitoring. GitHub holds the source and runs review checks. Distribute Chrome extension 1.4.0 as an unpacked package to authorized testers.

This is a personal, non-commercial academic demonstration. The free services can suspend, wake slowly or reject requests at their limits. Treat this as a capacity-limited demonstration. The published design keeps the site on a separate origin without API access. The target recurring cost is **₹0** within the free quotas. Provider accounts, public URLs and hosted measurements require owner-authorized provisioning. Historical provider comparisons and local Compose instructions are retained in the [previous readiness revision](https://github.com/505kjj/ThreatDetection/blob/ec7d5790aa7111ac97e4b78ee26745f96642d80e/docs/phase-8a-deployment.md).

## Before provisioning

- Confirm the project owner authorizes public Vercel and Render URLs, the named free accounts, use of the GitHub repository, the chosen region and publication of an operator privacy contact. Use the provider's sign-in flow. Keep vendor credentials in the vendor account or approved secret storage.
- Verify Vercel Hobby eligibility in the owner's account and confirm this project remains personal and non-commercial. Create a standalone free Render workspace without a payment method. Keep automatic deployments and Blueprint Auto Sync off. Use one Render service and one disposable Neon project. Keep paid upgrades, external reputation imports and scheduled wake traffic disabled.
- Use the exact release commit from the verified draft. Preserve branch protections and review requirements. The [GitHub verification workflow](../.github/workflows/release-verification.yml) checks the build without deployment credentials. A public preview URL also requires approval.
- Install the existing extension package into the Chrome profile used for staging. In `chrome://extensions`, copy the actual 32-character extension ID. An unpacked extension can receive a different ID when its path or installation changes. Restrict testing to the configured install.

## Neon Free

1. In the approved account, create a new Free project and a disposable database dedicated to this demonstration. Choose a region close to Render Singapore when that pairing is available on the approved Free account. Avoid connecting any existing user database.
2. Using a temporary database owner connection, provision an unprivileged LOGIN role. Create it through SQL or an approved database admin tool to avoid granting implicit provider administrator roles. Grant CONNECT only where needed, plus USAGE and CREATE on the demonstration database's application schema. Startup Flyway creates and owns its tables there. Keep table access and role membership isolated. Do not grant provider admin, database creation, role creation or superuser privileges to the app role. Have the operator set a distinct password in the protected provider workflow.
3. Choose the **direct** endpoint in Neon's Connect dialog. The application runs Flyway at startup and owns a two-connection Hikari pool. A direct endpoint preserves session semantics for Flyway and works for logical backup and restore. The transaction pooler is a future runtime option if migrations move to a separate verified connection.
4. Give Render a JDBC URL of the form `jdbc:postgresql://<direct-neon-host>/monitoring`. Put the user and password in separate Render variables. Keep credentials and options out of the URL. The frozen database policy uses pgJDBC `verify-full` with the container's CA bundle. Leave plaintext loopback bypass off. Verify the certificate and hostname from the running image and confirm the dedicated role can migrate and use only the demonstration schema.
5. Record the initial compute, storage and network-transfer counters. Prepare an encrypted logical backup using the direct endpoint and `pg_dump --format=custom`. Use environment or a protected client password file for credentials. Restore to a new disposable database with `pg_restore --exit-on-error --no-owner`. Validate Flyway history, report totals and scope before pointing any service at a restoration. Use the Free plan's restore history as a short recovery window and perform an independent export before testing provider-side suspension.

The 14-day monitoring retention runs at application startup and on its normal schedule when the backend is available. Short-lived activity sessions remain in H2 memory. The local Windows profile still defaults to its existing private H2 store. [Neon TLS](https://neon.com/docs/connect/connect-securely) · [Direct and pooled endpoints](https://neon.com/docs/connect/connection-pooling) · [Windows setup](windows-local-setup.md)

## Render Free

1. In the approved workspace, link the repository and select the verified deployment branch. Use [render.yaml](../render.yaml) as the Blueprint or enter its settings manually. Confirm the Free instance, one replica, Java 21 Docker build from the repository root and `/api/health` as liveness. Blueprint import can create a public URL. Leave Auto Sync and service auto-deploy off for subsequent changes. When deploying choose the verified commit explicitly.
2. Generate two independent 32-byte random base64url tokens. Give the authorized tester only the browser token. Give the operator the administrator token through a private channel. Store only their lowercase SHA-256 digests in Render. Keep tokens out of CLI arguments, logs, GitHub, Vercel, screenshots and URLs. See the [secure local setup guide](windows-local-setup.md) for the existing credential model.
3. Enter the following in the protected Render environment. Enable the `render` Spring profile. Render supplies `PORT` and Spring binds to `0.0.0.0` inside the container.

| Render variable | Value |
| --- | --- |
| `TD_RENDER_NEON_JDBC_URL` | Direct Neon JDBC endpoint and database name |
| `TD_RENDER_NEON_USER`, `TD_RENDER_NEON_PASSWORD` | Dedicated demonstration database role |
| `TD_RENDER_EXTENSION_ORIGIN` | Exact `chrome-extension://<actual-installed-id>` with no trailing slash |
| `TD_RENDER_BROWSER_DIGEST`, `TD_RENDER_ADMIN_DIGEST` | Independent lowercase SHA-256 digests |
| `SPRING_PROFILES_ACTIVE` | `render` |

4. The profile preconfigures the enrolled browser as synthetic. Keep the token private and use authorized controlled fixture sessions. Only the administrator token may read monitoring. Omit the public website origin from API CORS. The console is served at `/monitor` on the Render HTTPS origin and stores the sign-in token in memory. Log only sanitized outcomes.
5. The [Render Dockerfile](../deploy/Dockerfile.render) uses digest-pinned Temurin Java 21 bases, non-root UID 10001, the Linux CA bundle, the existing packaged dashboard and [measured JVM flags](../deploy/render-jvm.options). It copies only needed application assets. Confirm source revision and image in the provider logs before accepting traffic. The Docker configuration is separate from the local Compose build and Windows launch scripts. Provider-linked credentials have no build-time use.

### Reputation evidence

The default service starts without an active reputation feed. Report this as protection unavailable. Financial advisories can still run. Keep the website synthetic demo available independently.

For a restricted staging exercise, place a small, authorized synthetic snapshot in a Render Secret File, set `THREAT_REPUTATION_SNAPSHOT_PATH=/etc/secrets/<filename>`, and redeploy the verified commit. Render mounts the file under `/etc/secrets`. Confirm the JVM user can read it. The image excludes the secret file from its Docker build inputs. Respect the combined 1 MB provider limit, short fixture validity and existing snapshot validation and reload rules. Use only reserved example hosts and authorized local fixtures. When the exercise ends, remove the setting and file and redeploy the same commit so staging indicators cannot be mistaken for real protection.

For an authorized real feed, obtain browser redistribution rights and review the existing signed publication workflow. Use only a provider path or approved mounted file that remains recoverable after restarts. The free filesystem loses local writes after redeploys, restarts and spin-down. The default configuration does not enable live feed ingestion. [Render Docker secrets](https://render.com/docs/docker-secrets) · [Snapshot workflow](url-reputation.md)

## Vercel Hobby

1. After owner approval, verify eligibility, sign in to the Hobby account and connect only the approved GitHub repo if using Git integration. Keep automatic builds disabled and use manual releases from the exact checkout. If repository ownership prevents a Hobby Git integration, use an authorized Vercel CLI deploy from the same Git revision. Keep the repo root as the build root so the existing Inter and mark assets are available.
2. Add two approved build variables. `THREAT_PUBLIC_MONITOR_URL` must be the actual Render HTTPS URL ending in `/monitor`. `THREAT_PUBLIC_OPERATOR_EMAIL` must be the owner's approved public contact. Both values appear in public HTML. The hosted build fails before writing files if either value is missing or malformed. Configure the project as Other with Node 24 and use [vercel.json](../vercel.json). The configured command is `node website/build.mjs --vercel` and the output is `website/dist`.
3. Confirm the Vercel CLI upload honors [.vercelignore](../.vercelignore) or link the approved project. Only the generated static output is served. Git deployments are disabled in the project config. The hosted build requires an empty output directory, so use a clean checkout of the verified commit. After approval, link the checkout to the approved project, run `vercel pull --environment=production`, `vercel build --prod` and `vercel deploy --prebuilt --prod`. Record the deployment fingerprint and actual `vercel.app` URL.
4. Verify all ten routes with and without trailing slash, desktop and mobile layouts, keyboard and reduced-motion interactions, and a custom error page returning HTTP 404. Verify the CSP, no-referrer, frame policy and nosniff headers. Verify `/monitor`, `/api/health`, `/api/threat/monitoring/dashboard` and repository paths return 404 on Vercel. Validate the public privacy contact link and the exact administrator link. [Vercel routes](https://vercel.com/docs/build-output-api/configuration) · [Git settings](https://vercel.com/docs/project-configuration/git-configuration) · [Vercel deployment CLI](https://vercel.com/docs/cli/deploy)

## Hosted acceptance

Use an approved disposable browser profile, synthetic dataset and fresh scoped database. Capture desktop and mobile Vercel pages, the extension popup and warning pages, and the authenticated dashboard with synthetic data. Keep credentials and profile directories out of screenshots.

1. From Vercel, follow the installation guide. Load the verified ZIP's contents unpacked. Confirm Chrome ID. Set the approved Render HTTPS origin in extension settings, accept the native HTTPS grant for that host, enter the browser token and run Test connection.
2. Check HTTPS and security headers and confirm `401` without a token. Confirm the browser role cannot read administrator reports and the admin role cannot post a browser heartbeat or obtain a snapshot. Verify only the admitted Chrome origin passes API CORS, including rejection of a second synthetic extension ID.
3. On controlled fixtures check confirmed reputation blocking, the one-time eligible phishing bypass, malware no-bypass, financial advisories, pause/resume and warning details. Exercise missing snapshot, expiration, still-valid cached evidence and recovery. Check absent evidence is shown as unavailable.
4. Enable monitoring, send one authorized synthetic event and open `/monitor` using the distinct administrator token. Confirm synthetic counts update and real scope stays empty. Replay the same event ID and verify no second count. On a disposable tenant with provider approval, test bounded rate limiting and opt out, then confirm fresh sends stop. Restart once and check stored records and re-established browser state.
5. Leave Render idle beyond its stated interval and Neon idle beyond its own interval. Record natural cold requests, dashboard recovery and extension timeouts. Perform a bounded Neon outage and recovery in the disposable project and confirm storage unavailable, recovery, deduplication, logical restore and retention. Avoid periodic requests that keep services awake. Some Hikari connections may remain open while the service is awake, so check wake latency from provider metrics and isolated first requests.
6. Record cold JVM startup, request median/p95/p99, DB connection latency, dashboard load, bounded write concurrency, storage growth, provider resource use and errors. Review both dashboard themes, motion, chart keyboard controls, a live screen reader and the original dashboard design reference when available. Confirm experimental protection is disabled. Provider uptime and capacity conclusions require hosted evidence.

If Render is asleep, one ordinary request starts the service. It can take around a minute, which exceeds the extension's current five-second request timeout. The UI should show unavailable or offline as appropriate. Retry manually after the dashboard is ready. Neon wake or quota failures should surface as startup failure or monitoring unavailable. The PostgreSQL Hikari pool validates connections on borrow and sends no idle keepalive queries. Check provider dashboards, use clean snapshots and keep valid cached browser protection within existing expiry rules.
